# Frontend Slides

创建零依赖、动画丰富、完全在浏览器中运行的 HTML 演示文稿。

## 核心原则

1. **零依赖**——单个 HTML 文件，CSS/JS 内联。不用 npm，不用构建工具。
2. **展示而非讲述**——生成可视化预览，而不是抽象选项。人们通过看来发现自己想要什么。
3. **独特设计**——拒绝平庸的"AI 垃圾风格"。每一份演示文稿都必须有量身定制的感觉。
4. **渐进披露**——先读轻量的风格索引。对 bold 模板，用小预览卡做风格预览，只在用户选定该模板后才加载完整的 `design.md`。
5. **固定 16:9 舞台（不可协商）**——每一份演示文稿都使用 1920×1080 幻灯片画布，作为整体缩放到视口。幻灯片在所有屏幕（包括手机）上都必须保持 16:9。不要为适配设备而重排幻灯片内容。

## 设计美学

你往往会收敛到平庸、"随大流"的输出。在前端设计中，这会造出用户所说的"AI 垃圾风格"审美。要避免这一点：做出有创意、有辨识度、令人惊喜愉悦的前端。

专注于：

- 字体排印：选择优美、独特、有趣的字体。避免 Arial、Inter 这类平庸字体；转而选择有辨识度、能抬升前端审美的字体。
- 色彩与主题：坚定采用一套连贯的审美。用 CSS 变量保持一致性。主导色配锐利强调色，胜过怯懦而均匀分布的调色盘。从 IDE 主题和各类文化美学中汲取灵感。
- 动效：用动画实现效果与微交互。HTML 优先采用纯 CSS 方案；React 场景在可用时使用 Motion 库。聚焦高影响力时刻：一次编排得当、带交错入场（animation-delay）的页面加载，比零散的微交互带来更多愉悦。
- 背景：营造氛围与纵深，而不是默认用纯色。叠层 CSS 渐变、使用几何图案，或添加与整体审美相符的情境化效果。

避免平庸的 AI 生成式审美：

- 被用滥的字体族（Inter、Roboto、Arial、系统字体）
- 陈词滥调的配色（尤其是白底紫色渐变）
- 可预测的布局与组件套路
- 缺乏语境个性的流水线式设计

富有创造性地诠释，做出令人意外、却真正为该语境量身设计的选择。在明暗主题、不同字体、不同美学之间做出变化。你仍会在多次生成中倾向于收敛到常见选择（例如 Space Grotesk）。要避免这一点：跳出框框思考至关重要！

## 固定舞台规则

以下不变式适用于每一份演示文稿中的每一页幻灯片：

- 每一份演示文稿都有一个填满浏览器窗口的视口包裹层。
- 每一页幻灯片都在固定的 1920×1080 舞台内编写。
- 舞台整体等比缩放以适配视口。可以留黑边（letterbox/pillarbox）；绝不能重新布局内容。
- 不要用响应式断点为手机重排幻灯片内容。
- 按 1920×1080 设计尺寸使用固定的幻灯片内部度量。
- 幻灯片可见性必须由 `.active` / `.visible` 控制，使用 `viewport-base.css` 中的 `visibility`、`opacity` 和 `pointer-events`。不要用 `display: none` / `display: block` 切换幻灯片；后出现的布局类（如 `.slide-content { display: flex; }`）可能覆盖它们，导致所有幻灯片同时可见。
- `clamp()` 只能用于舞台之外的非幻灯片 UI，或在完整舞台不现实的小型兜底预览中。
- 包含对 `prefers-reduced-motion` 的支持
- 绝不直接对 CSS 函数取负（`-clamp()`、`-min()`、`-max()` 会被静默忽略）——改用 `calc(-1 * clamp(...))`

**生成时，读取 `viewport-base.css` 并把它的完整内容包含进每一份演示文稿。**

### 内容密度模式

询问用户这主要是一份供阅读的还是供演讲的演示文稿，然后围绕这个答案设计：

| 密度模式              | 最适合                             | 设计行为                                                                                                     |
| --------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **低密度 / 演讲主导** | 公开演讲、主题演讲式分享、现场讲解 | 每页一个观点、大字号、强视觉层级、充足留白、最多 1-3 条要点、需要时增加页数                                  |
| **高密度 / 阅读优先** | 报告、讲义、异步评审、详细内部文档 | 更多自成一体的幻灯片、结构化网格/表格/标注、在可读的前提下 4-8 条要点或 4-6 张卡片、更紧凑但仍刻意安排的间距 |

基线限制依然适用：不滚动、不溢出、面板不重叠、文字不得低于舒适的阅读字号。如果内容超出所选密度模式，就拆成更多页，而不是一路缩小到拥挤为止。

## 阶段 0：判断模式

判断用户想要什么：

- **模式 A：新建演示文稿**——从零创建。进入阶段 1。
- **模式 B：PPT 转换**——转换 .pptx 文件。进入阶段 4。
- **模式 C：增强**——改进现有 HTML 演示文稿。阅读它、理解它、再增强。**遵循下方模式 C 修改规则。**

### 模式 C：修改规则

增强现有演示文稿时，固定舞台下的内容适配是最大风险：

1. **添加内容之前：**清点现有元素，对照密度限制检查
2. **添加图片时：**把图片放进 1920×1080 幻灯片画布内。如果该页内容已到上限，拆成两页
3. **添加文字时：**每页最多 4-6 条要点。超限了？拆成续页
4. **任何修改之后，都要验证：**幻灯片舞台保持 16:9、没有文字溢出所在卡片、没有面板重叠，并且在 1280×720 外加一个手机视口下的截图看起来正确
5. **主动重组：**如果修改会导致溢出，自动拆分内容并告知用户。不要等用户开口

**向现有幻灯片添加图片时：**先把图片移到新页，或先削减其他内容。绝不在未检查现有内容是否已填满 1920×1080 幻灯片舞台的情况下添加图片。

## 阶段 1：内容发现（新建演示文稿）

**把所有问题一次性一起提出**，让用户一次填完全部。如果当前环境提供原生结构化提问 UI，就用它；否则在一条简洁消息里提问，并给出清晰编号的选项：

**问题 1——用途**（header: "用途"）：
这份演示文稿用于什么？选项：路演稿 / 教学教程 / 会议演讲 / 内部演示

**问题 2——篇幅**（header: "篇幅"）：
大约多少页幻灯片？选项：短篇 5-10 / 中篇 10-20 / 长篇 20+

**问题 3——内容**（header: "内容"）：
内容准备好了吗？选项：全部内容就绪 / 粗略笔记 / 只有主题

**问题 4——密度**（header: "密度"）：
演示文稿的密度应该是什么感觉？选项：

- "低密度 / 演讲主导"——大想法、更少的文字、更多视觉呼吸空间
- "高密度 / 阅读优先"——更多自成一体的细节，便于异步阅读

**不要在阶段 1 询问行内编辑。**用户不应在看到草稿之前就选择编辑行为。行内编辑是草稿之后再提供的能力：默认包含，除非用户明确要求锁定/仅导出的文件。

记住用户的密度选择。它影响幻灯片页数、字号比例、每页文字量、布局密度，以及偏向电影感的演讲页还是自成体系的阅读页。

如果用户已有内容，请他们分享。

### 步骤 1.2：图片评估（如果提供了图片）

如果用户选择了"无图片"→ 跳到阶段 2。

如果用户提供了一个图片文件夹：

1. **扫描**——列出所有图片文件（.png、.jpg、.svg、.webp 等）
2. **逐张检视**——使用助手可用的图像理解能力。如果无法读取图片，则依据文件名/元数据，仅在需要时请用户澄清
3. **评估**——每张图片：它展示什么、可用还是不可用（附原因）、它代表什么概念、主色调
4. **共同设计大纲**——精选图片与文字一起决定幻灯片结构。这绝不是"先规划幻灯片再加图片"——从一开始就同时围绕两者设计（例如 3 张截图 → 3 页功能页，1 个 logo → 标题页/结尾页）
5. **确认大纲**——在可用时使用同样的结构化提问机制："这份幻灯片大纲和图片选择看起来合适吗？"选项：没问题 / 调整图片 / 调整大纲

**预览中的 logo：**如果识别出了可用的 logo，就把它（base64）嵌入阶段 2 的每个风格预览——用户会看到自己的品牌以三种不同方式呈现。

## 阶段 2：风格发现

**这是"展示而非讲述"的阶段。**大多数人无法用语言说清自己的设计偏好。

### 步骤 2.0：直接生成 3 个风格预览

基于用途、受众、情绪和内容密度，生成 3 个互不相同的单页 HTML 预览，展示字体排印、色彩、动画和整体审美。

不要问用户是想要多个选项还是预设选择器。默认的发现体验始终是视觉对比。

如果用户已经给出了基调，就直接用。如果没有，就从场合、受众、内容和分量推断可能的情绪。让选项足够多样，用户能直接凭视觉反应，而不必预先用语言表达品味。

如果用户明确点名某个预设或 bold 模板，就把它作为一个选项，并围绕它生成其余预览位。

预设候选见 [STYLE_PRESETS.md](STYLE_PRESETS.md)。

| 情绪          | 建议预设                                           |
| ------------- | -------------------------------------------------- |
| 印象深刻/自信 | Bold Signal, Electric Studio, Dark Botanical       |
| 兴奋/充满活力 | Creative Voltage, Neon Cyber, Split Pastel         |
| 平静/专注     | Notebook Tabs, Paper & Ink, Swiss Modern           |
| 受启发/被打动 | Dark Botanical, Vintage Editorial, Pastel Geometry |

**预览组合规则：**

- 默认生成 3 个预览：1 个来自 `STYLE_PRESETS.md` 的稳妥预设、1 个推向更强视觉个性的预设变体、1 个 wildcard。
- wildcard 是自行生成的自定义设计。让它成为针对用户场合、受众、情绪和内容的最强、最有用的对比项。
- 不要强求每个富有表现力的选项都出自模板库。如果这份需求简报比现有模板蕴含更锐利、更具体的设计机会，就用 wildcard 位自由设计。
- 对于保守或高风险的演示文稿，让稳妥预设格外克制；让预设变体保持沉稳正式；让 wildcard 是有权威感而非装饰感的自定义设计。
- 对于富有表现力的演示文稿，让稳妥预设保持可读的兜底；选一个强力的 bold 模板；让 wildcard 大胆、贴合语境，并与另外两个预览明显不同。
- 如果 bold 模板的匹配显得牵强，就改用 wildcard 做自定义设计，或退回另一个稳妥预设，不要硬套模板。

**自定义 wildcard 设计规则：**

- 遵循上文的设计美学一节：不搞平庸的"AI 垃圾风格"，不用默认的字体/配色/布局选择，不搞白底紫渐变的陈词滥调，不搞千篇一律的仪表盘/卡片观感。
- 契合用户说明的场合、受众、情绪/基调和内容密度。自定义设计应让人觉得是专为这份演示文稿而作，而不只是"好看时髦"。
- 做出明确的视觉主张：有辨识度的字体排印、贯彻到底的调色盘、可识别的布局系统，外加一个强有力的氛围性或图形化手法。
- 保证它撑得起一整份演示文稿。预览必须暗示出一套能扩展出章节页、内容页、引言页、对比页和结尾页的设计系统。
- 遵循固定 1920×1080 舞台规则，并和其他每个选项一样通过同样的预览真实性检查。
- 绝不在幻灯片上渲染"custom"、"wildcard"、"AI-generated"或设计流程标签。

**bold 模板选择规则：**

- 把用户用途和情绪与 `mood`、`tone`、`best_for`、`avoid_for`、`formality`、`density`、`scheme` 逐项匹配。
- 把 `best_for` 示例当作软性参考，不是严格的行业筛选条件。
- 三个预览要彼此真正不同。
- 选定 bold 模板候选后，只从选择索引中的 `preview_md` 路径读取那些候选的 `preview.md` 文件。
- `preview.md` 只用于标题页预览。用户选定最终模板之前，不要读取完整的 `design.md` 文件。
- 除非选定的最终 `design.md` 缺少关键实现细节，否则不要读取或复制 `template.html`。

**预览真实性规则（不可协商）：**

- 每个风格预览都必须看起来像用户演示文稿真正的首页，而不是一张诊断卡片。
- 绝不在幻灯片上渲染内部流程文字：不得出现 `preview`、`generated from`、`preview.md`、`template`、`preset`、`style option`、`Option A/B/C`、文件名、路径或来源文档标签。
- 绝不在幻灯片上渲染模板名或 slug 名。模板/风格名称只应出现在发给用户的消息里。
- 绝不把用户需求备注渲染成幻灯片内容，例如"尖锐挑衅"、"稳妥选项"、"大胆选项"、"仅供内部分享"或"audience: ..."，除非用户明确要求该短语出现在演示文稿里。
- 如果幻灯片需要装饰性界面元素（chrome），只使用真实的演示文稿装饰：演示文稿标题、章节标题、日期、作者、公司、页码，或来自用户材料的真实内容短语。
- 打开预览前，检查可见文字，出现任何内部元数据就修改。

把预览保存到 `.frontend-slides/slide-previews/`（style-a.html、style-b.html、style-c.html）。每个都应自包含、紧凑，展示一页带动画的标题页。

沙箱里没有图形界面，不要用 `open` 命令。把三个预览文件作为附件送达聊天（一对一 `cp` 进 `$AGENT_OUTBOX/`；群里随消息附 post `files`），再按步骤 2.1 让用户在聊天里选择。

### 步骤 2.1：用户选择

询问（header: "风格"）：
你更喜欢哪个风格预览？选项：风格 A：[名称] / 风格 B：[名称] / 风格 C：[名称] / 混合元素

如果选了"混合元素"，询问具体想法。

## 阶段 3：生成演示文稿

用阶段 1 的内容（文字，或文字 + 精选图片）和阶段 2 的风格生成完整演示文稿。

如果提供了图片，幻灯片大纲已在步骤 1.2 中纳入它们。如果没有，CSS 生成的视觉元素（渐变、形状、图案）提供视觉趣味——这是一条完全受支持的一等路径。

在整份演示文稿中贯彻用户的密度选择：

- **低密度 / 演讲主导：**用更多页数、每页更少的观点。偏好大标题、短语、视觉隐喻、章节节拍、引言/宣言页，以及便于演讲者掌控的节奏。
- **高密度 / 阅读优先：**让幻灯片更加自成一体。用结构化网格、对比表格、带标注的图示、图注和简洁的说明文字。保持强层级，让它有设计感，而不是像一份贴到幻灯片上的文档。

如果用户的需求是混合的，就选两种模式中更接近的一种，而不是发明一个中间选项：面向现场观众的说服默认低密度；异步传阅或详细评审默认高密度。

绝不让高密度变成视觉杂乱。某页高密度幻灯片开始溢出时，就拆分它，或重新设计成更清晰的结构。

如果用户选了预设变体，把它的 `STYLE_PRESETS.md` 定义当作设计配方：

- 保留它的字体、调色盘、装饰语汇、间距节奏和组件语法。
- 无论源模板原本使用 `deck-stage.js` 还是视口流式 CSS，都把最终演示文稿生成为固定 1920×1080 舞台，整体等比缩放到视口。
- 把 `design.md` 中的视口流式值当作设计比例，换算成 1920×1080 舞台坐标。不要在最终演示文稿中把它们保留为实时的视口重排规则。
- 输出保持为单个自包含的 Frontend Slides HTML 文件。
- 不要复制演示幻灯片内容，也不要过于刻板地模仿源模板。
- 只把 `template.html` 当作所选模板的最后手段实现参考。
- 生成后，在渲染出的浏览器截图中同时验证内容溢出与面板重叠。只检查 `scrollHeight` 不够，因为网格面板可能在视觉上互相遮盖。

如果用户选了自行生成的自定义 wildcard，把该预览的 CSS 和布局当作设计配方：

- 保留它的字体、调色盘、装饰语汇、间距节奏、网格逻辑和组件语法。
- 把同一视觉系统扩展到整份演示文稿。用户已选定自定义方向后，不要再切换到预设或 bold 模板。
- 缺失的幻灯片版式从该系统中设计，而不是从别的风格导入套路。
- 输出和其他所有演示文稿一样：固定舞台、单文件、经过视觉验证。

**生成之前，阅读以下支撑文件：**

- [html-template.md](html-template.md)——HTML 架构与 JS 特性
- [viewport-base.css](viewport-base.css)——强制 CSS（完整包含）
- [animation-patterns.md](animation-patterns.md)——对应所选感觉的动画参考

**关键要求：**

- 单个自包含 HTML 文件，所有 CSS/JS 内联
- 在 `<style>` 块中包含 viewport-base.css 的完整内容
- 使用 Fontshare 或 Google Fonts 的字体，但字体栈末尾必须带系统字体回退——交付走文件管道，用户多在内网/国内网络，外部字体加载不到时靠回退保证可读，排版不要依赖特定字体加载成功
- 添加详细注释解释每个区块
- 每个区块都要有清晰的 `/* === SECTION NAME === */` 注释块

## 阶段 4：PPT 转换

转换 PowerPoint 文件时：

1. **提取内容**——解压 .pptx（它是一个 zip 归档），读取 `ppt/slides/*.xml` 获取文字、`ppt/notesSlides/*.xml` 获取演讲者备注，并从 `ppt/media/` 复制图片
2. **与用户确认**——呈现提取出的幻灯片标题、内容摘要和图片数量
3. **风格选择**——进入阶段 2 进行风格发现
4. **生成 HTML**——转换成所选风格，保留全部文字、图片（来自 assets/）、幻灯片顺序和演讲者备注（以 HTML 注释形式）

---

## 阶段 5：交付

1. **清理**——删除 `.frontend-slides/slide-previews/`（如果存在）
2. **交付**——把最终 HTML 复制进 `$AGENT_OUTBOX/`，让它以附件送达聊天、点开即可翻页（群里随消息附 post `files`，outbox 不生效）；命名与话术统一见 artifact-delivery 技能
3. **总结**——告诉用户：
   - 文件名、风格名称、幻灯片页数
   - 导航方式：方向键、空格键、（如启用）滑动/点按
   - 如何自定义：颜色用 `:root` CSS 变量、字体排印用字体链接、动画用 `.reveal` 类
   - 提供行内文本编辑：悬停左上角或按 E 进入编辑模式，点击任意文本进行编辑，Ctrl+S 保存
   - 主动提供草稿之后的自然后续动作：请求修改、在浏览器里直接编辑文本，或导出/分享

---

## 阶段 6：分享与导出（可选）

这份演示文稿是单个自包含的 HTML 文件。要分享，直接发送文件本身（聊天附件、邮件）——接收者在任何浏览器中打开即可，无需安装。要生成 PDF，可在浏览器中打开演示文稿并使用 打印 → 另存为 PDF（横向、无边距、开启背景图形）。
